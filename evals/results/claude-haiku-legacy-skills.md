### legacy-stack-playbooks / stack-adelia-generated / baseline / PASS

Reading the generated RPG is a good starting point, but it shouldn't be the only source. Generated code is what runs, but it's a derived artifact. Inventory from it alone and you'll miss what matters most for a migration.

**Why generated RPG alone isn't enough**

- **The Adelia model is the source of truth.** Business rules, screen and report definitions, data relationships, and validation usually live in Adelia's model and generator metadata. The generated RPG is a translation of that model, often hard to read and full of framework scaffolding. Migrating from it means migrating the output of a tool you may be replacing.
- **Regeneration hides changes.** Hand edits to generated code can be lost on the next generation, or you may find manual changes in the output that aren't in the model. You need to know which is the real logic.
- **Generated code is a poor map of usage.** Dead objects, unused screens, and batch jobs that run on schedules are easier to find from runtime data and the object catalog than from reading source.

**Recommended approach**

1. **Get the sources of truth.** Find the Adelia project/model repository, the generator configuration, and any customizations or exits. Confirm with the team which artifacts they edit: the model, the generated source, or both.
2. **Inventory the generated output on the IBM i.** Pull the RPG source members and the compiled objects (programs, service programs, modules, binding directories) from the libraries. Compare the generated source against the model to detect drift.
3. **Catalog the database layer.** List the physical and logical files, their keys, and relationships (DDS or SQL DDL). Use the IBM i catalog views such as `QSYS2.SYSTABLES`, `QSYS2.SYSCOLUMNS`, and `QSYS2.SYSINDEXES` for SQL-visible objects.
4. **Inventory the non-RPG pieces.** Include CL programs, display files, printer files, SQL procedures and functions, data areas, data queues, job descriptions, and scheduled jobs. Generated apps often depend on these.
5. **Map dependencies.** Use the program-to-file references and the binding information to build a call graph. Adelia frameworks often hide a lot of this behind shared service programs.
6. **Check runtime usage.** Use job schedules, job logs, and object usage data (for example, last-used information from the object statistics views, if your system collects it) to identify what is actually executed. Some code paths may never run.
7. **Record the business meaning.** Map screens, menus, and batch jobs to business functions, and get owners to validate them. The code tells you what it does, not why.
8. **Produce the inventory.** Build a table per object: name, type, source location, model element it came from, callers, data touched, last-used date, owner, and migration disposition (rewrite, retain, retire).

**Caveats**

- I haven't verified Adelia-specific details (its model format, generator outputs, or how it exposes metadata) in this exercise. Confirm them with the Adelia documentation or the vendor.
- Check that your inventory scripts and queries are read-only, and run them in a non-production environment if you have one.

If you can tell me how the team stores the Adelia model and what the generated objects are named, I can help you design the inventory schema or the catalog queries.

**Why generated RPG alone is incomplete**

- **The model is the real source.** Adelia regenerates code from its own definitions (screens, file/dictionary definitions, rules, and any custom code hooks). Business intent is easier to find there. - **Source on the machine may not match what's deployed.** Source members and compiled objects can drift apart.

**Proposed approach**

1. **Establish the source of truth.** Find the Adelia project or model repository, and check whether Adelia can export its metadata (check its documentation or export features). Confirm that the generated source in the source physical files is the output of the current model.

2. **Confirm what is deployed.** Compare the compiled objects in production libraries with the source members:
   - Use `QSYS2.OBJECT_STATISTICS` (or `DSPOBJD`) to list objects, types, sizes, creation and change dates, and last-used timestamps.
   - Use `DSPPGMREF` (to an outfile) to build a program-to-program and program-to-file reference map.
   - Flag objects that have not been used in a long time as candidates for retirement, after checking that last-used data covers a sufficient period (including month-end and year-end runs).

3. **Inventory the runtime surface, not just the source:**
   - **Programs and modules:** RPG, CL, SQL procedures, service programs, and their call relationships.
   - **Data:** physical and logical files (DDS or DDL), their record formats, keys, and relationships. Use `QSYS2` catalog views such as `SYSTABLES` and `SYSCOLUMNS`.
   - **User interface:** display files, menus, and Adelia screen definitions.
   - **Job control:** job scheduler entries, subsystems, job queues, and data areas.
   - **Integrations:** data queues, message queues, IFS interfaces, EDI, file transfers, web services, and any database or program calls from outside the system.
   - **External callers:** ODBC/JDBC clients, reporting tools, and other systems that read or write the data.

4. **Parse the generated RPG for structure.** Once you have the source, extract the following with a script or a static analysis tool:
   - `CALL`, `CALLB`, `CALLP`, and procedure prototypes
   - file declarations (`Dcl-F`, F-specs) and I/O operations
   - `/COPY` and `/INCLUDE` members, which often hold shared Adelia runtime code
   - `EXFMT` and display file usage

5. **Validate with runtime evidence.** Use job logs, database monitors (`STRDBMON`), and journal data to see which paths actually execute. Static analysis finds code that might run, and runtime data shows what does run. Use both to prioritize migration and to find dead code.

6. **Handle the source with care.** Source members often contain hard-coded credentials, connection strings, or sensitive business data. Apply your data-handling policy before copying members off the system, and store the inventory in a controlled location.

**What the finished inventory should contain**

- A list of objects with their type, library, source origin (Adelia model element vs. hand-written code), last-used date, and owner
- A call and data-access graph, including external entry points
- The data model and its owners
- The list of interfaces and scheduled jobs
- A list of unknowns, such as objects with no recorded use or code that cannot be traced to a model element

**Migration consideration:** If the target is not Adelia-based, the model is probably the more useful input for redesign, while the runtime data and generated code are better for finding behavior that must be preserved.

### legacy-stack-playbooks / stack-symfony-hidden-rules / baseline / PASS

Before you port or write tests from the docs, I'd check the things that documentation usually leaves out. In most Symfony apps, the behavior that matters most lives in code the docs don't describe.

**1. Treat the docs as a starting point, not the spec.**
Docs often lag the code. Write characterization tests that run against the existing Symfony app and record what it actually does: status codes, response bodies, redirects, and database side effects. Use those recordings as the reference for your port. Tests written only from docs will miss real behavior.

**2. Hidden behavior: events, listeners, and subscribers.**
Check `src/EventListener`, `src/EventSubscriber`, and the `kernel.*` and Doctrine lifecycle events (`prePersist`, `postUpdate`, `onFlush`, and so on). These often send emails, adjust stock, recalculate totals, or log audit entries, and they rarely appear in controller or entity docs.

**3. Money and arithmetic.**
Find every place prices, taxes, discounts, shipping, and currency are computed. Check whether the app stores money as integers (cents) or floats/decimals, how it rounds, the order of operations (discount before or after tax), and whether currency conversion happens anywhere. Port these with exact test vectors, including edge cases like rounding half-cents and zero-value items.

**4. Database schema and Doctrine mapping details.**
Read the actual migrations (`migrations/`), not just the entity annotations. Check for:
- Cascade and orphan-removal settings
- Lazy vs. eager loading and the N+1 queries this causes
- Custom types, indexes, unique constraints, and soft-delete patterns
- Default values set in the database rather than in code

**5. Security and access control.**
Review `config/packages/security.yaml`, voters, access-control rules, password hashing config, CSRF checks on forms, and remember-me behavior. Auth and authorization are the most likely places for subtle regressions in a port.

**6. Forms and validation.**
Symfony form types often hold business rules: validation constraints, data transformers, and `*Type` classes with custom options. Validation messages and error ordering may be visible to users, so capture them.

**7. Session and cart state.**
Determine where the cart lives (session, database, or both), how it merges on login, and what happens to it on expiry. This is a common source of bugs when porting.

**8. Payment and external integrations.**
List every external call: payment gateways, shipping APIs, webhooks, and email. Check webhook signature verification and idempotency. Mock these at the HTTP boundary and replay real payloads.

**9. Async and scheduled work.**
Check Symfony Messenger handlers, transports, retry settings, Cron jobs and console commands (`src/Command`). These can run outside the request cycle and are easy to forget.

**10. Config, environment, and templates.**
Look at `.env` handling, `services.yaml` autowiring and aliases, parameters, Twig filters and extensions, and any translation domains. Templates often contain logic that the port must reproduce.

**Suggested order:**
1. Inventory: list routes, entities, listeners, commands, and external services.
2. Pick the highest-risk flows (checkout, pricing, payment, auth) and write characterization tests for them against the running Symfony app.
3. Port those flows first and run the same tests against the new stack.
4. Expand to the rest, keeping the Doctrine migrations as the authoritative schema.

**Date:** 2026-11-16
**Decision owner:** [Name / role]

## Context

The legacy system contains about 4,000 programs. A developer's code scan reports that about 1,500 are never called and proposes removing them from migration scope. Removing 37.5% of the inventory would significantly reduce migration effort, so the claim needs verification before it becomes scope.

## Decision

**Do not exclude the 1,500 programs yet.** Reclassify them as *"retirement candidates, pending verification."* They stay in scope until each one passes the verification gates below, or until the owning business unit formally signs off on retiring it.

## Rationale

A static "never called" result is a weak basis for permanent removal, for these reasons:

1. **Static analysis misses runtime invocation.** Common blind spots include:
   - Dynamic calls (computed program names, dispatch tables, reflection-like patterns)
   - Calls from job schedulers, JCL/batch streams, or cron-style triggers
   - Invocation from data-driven configuration or database-stored program names
   - Calls from other systems, integrations, EDI/file-drop handlers, or APIs
   - Entry points used only by human operators (ad hoc utilities, admin tools)
2. **Infrequent programs are not unused programs.** Year-end, quarter-end, regulatory, audit, tax, or disaster-recovery programs may run once a year or less. A scan that only looks at the current call graph would classify them as dead.
3. **The scan's scope is unknown.** We need to confirm whether it covered all source languages, copybooks, stored procedures, screens/maps, and scripts, and whether it treated inbound triggers as roots.
4. **Removal from migration scope is hard to reverse.** Once a program is dropped and its business logic is lost, recovering it means reverse-engineering. Deferring the decision costs much less than a missed critical function.

## Verification Gates

A program moves from "candidate" to "excluded" only when **all** of the following are true:

| Gate | Evidence required |
|---|---|
| **G1. Static confirmation** | Developer's scan results reviewed; scan covers all source types and entry points; false-positive sample checked (e.g., 50 random programs manually inspected) |
| **G2. Runtime evidence** | Execution/access logs, job-scheduler history, or transaction-monitor data covering at least one full business cycle (recommend 12–13 months to include annual and period-end jobs) show zero invocations |
| **G3. Trigger review** | Schedulers, JCL, cron, integration/ESB configs, and database-stored program references checked for references to the program |
| **G4. Data dependency check** | Program does not write to tables or files read by any in-scope program or report, or any such output is confirmed unused |
| **G5. Business owner sign-off** | The owning business unit confirms the function is obsolete or replaced |
| **G6. Archive** | Source and documentation archived in a read-only repository with the scan and log evidence |

Programs that fail any gate stay in scope. Programs that fail G2 but pass the others should be flagged as "rare-use" and handled in the migration design.

## Suggested Process

1. **Week 1–2:** Developer provides the scan methodology, the list of 1,500 programs, and the entry-point definitions used. Review a sample for false positives.
2. **Week 2–6:** Pull runtime logs and scheduler history. Run G3 and G4 checks against the candidate list.
3. **Week 6–8:** Business owners review grouped candidates by domain. Produce a final list split into *Excluded*, *Retained*, and *Rare-use*.
4. **Week 8:** Approve the revised scope and record the archive location.

If logs cover less than 12 months, classify candidates as "provisionally excluded," keep them archived, and set a review date after the next full cycle.

## Risks

- **Risk:** A critical annual or regulatory program is dropped.
  **Mitigation:** G2 requires a full business cycle; G5 requires business sign-off.
- **Risk:** Dependencies on dropped programs break in-scope programs.
  **Mitigation:** G4 data-dependency check.
- **Risk:** Scope reduction is treated as final before verification.
  **Mitigation:** Keep the archive and the "provisional" label until post-cutover validation.

## What Would Change This Decision

- If runtime logs for a full cycle show zero invocations and the other gates pass, the program can be excluded.
- If the scan proves to be complete and the method is validated against logs with a low false-positive rate, the verification effort can be reduced for future batches, though G2 and G5 still apply.

## Open Questions

1. Do we have runtime or job-scheduler logs, and how far back do they go?
2. Which entry points (batch, online, interfaces, APIs) did the scan treat as roots?
3. Who are the business owners for each functional domain?
4. Is there a regulatory or audit requirement for retaining program logic or documentation?
